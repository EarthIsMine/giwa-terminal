# 나루(NARU) 검증 런치패드 - 설계 및 구현 노트

> v2 (2026-07-22) · 구현 반영판. 초안(v1)은 퍼미션리스 본딩커브 모델이었으나
> "신원 검증 발행이 정체성" 팀 결정(2026-07-21, CLAUDE.md)과 충돌하여 폐기하고 전면 재작성했다.
> 이 문서는 `packages/contracts`에 실제 구현된 내용과 1:1로 대응하며, 기술 문서(제출물)의
> 런치패드 챕터 원본이 된다.

## 1. 제품 정의

나루 런치패드는 **신원 검증 발행 게이트**다. 밈코인 즉시 상장이 아니라:

```
발행 신청 (터미널 폼)
   → 오프체인 심사
   → 온체인 어테스테이션 (IdentityRegistry.attest)
   → 발행 + 상장 (TokenFactory.issueAndList, 1-tx)
   → 터미널 자산 보드 노출 (검증 배지와 함께)
```

기와 생태계에 아직 런치패드가 없으므로 선점하되, 기와의 정체성(신원 기반 규제 준수
체인 - 도장·GIWA ID·보자기)과 같은 방향을 본다. 검증 배지는 UI 장식이 아니라
온체인 원장(TokenFactory 레지스트리)에서 파생된다 (절대 규칙 6).

**데모 시드 봇과 제품이 같은 경로를 쓴다.** 시드 토큰도 운영자 어테스테이션을 받고
`issueAndList`로 발행된다 - 데모와 제품이 다른 물건이 되는 것을 구조적으로 방지.

### 1.1 왜 나루인가 - 포지셔닝과 기대효과

정직한 전제에서 출발한다: **런치패드와 터미널은 커모디티다.** 어떤 체인이든 열리면
런치패드가 생기고, GMGN·pump.fun류 터미널이 따라온다. 기능 목록으로는 차별화가
불가능하다. 나루의 논지는 세 개다.

1. **속도 - 기와 생태계 선점.** 기와에는 아직 런치패드도, 가격 데이터 표준도 없다.
   가격 레이어(인덱서·API)와 발행 게이트를 먼저 깔면, 이후 생태계 앱들이 우리
   레일 위에 올라온다. 커모디티 시장에서 선점자의 레일이 표준이 된다.
2. **한국 로컬라이제이션은 흉내로 안 된다.** GMGN류는 크립토 네이티브 문법이다 -
   지수 표기, MCAP/FDV, 5분 변동률, 수백 종 무한 스크롤. 나루의 타겟(업저씨)은
   그 문법 앞에서 이탈한다. 업비트 시세 기준 원화 환산, 일·월 단위 변동률, 낮은
   정보 밀도, 익숙한 한국어 UI 관습 - 이건 타겟 유저와 같은 시장에서 사는 사람이
   가장 잘 만들 수 있고, 그게 우리다.
3. **기와 기술 통합 - "누가 발행했는지 아는 DEX".** 온체인을 모르는 사람이 DEX를
   안 쓰는 근본 이유는 UI가 아니라 신뢰다. 익명 발행 대신 도장(Dojang)·GIWA ID
   신원 검증을 발행의 전제로 박아서 "검증된 주체만 올라오는 시장"을 만든다.
   이 설득 구조는 신원 기반 규제 준수 체인이라는 기와의 정체성과 정확히 겹치며,
   기와가 아닌 체인에서는 재현하기 어렵다 - 체인 선택 자체가 해자의 일부다.

기대효과: 업비트 유저의 첫 온체인 경험 관문(브리지→터미널→검증 자산), 기와
생태계의 가격 데이터 표준 선점, 그리고 검증 발행 레일의 사실상 표준화.

### 1.2 양면 게이트 - 참여자 검증 (팀 제안 채택, 2026-07-22)

바이낸스가 증명한 사다리(Wallet TGE → 알파 → 선물 → 현물)를 레퍼런스하되,
참여 게이트의 기준을 바꾼다. 바이낸스의 게이트는 알파 포인트(활동·자산 규모)라
포인트 파밍·볼륨 워싱 부작용을 낳았다. 나루의 게이트는 **업비트 아이디 KYC
신원**이다 - 실명 기반이라 1인 1자격이 구조적으로 보장되고, 파밍 유인 자체가
없다. 이로써 시장의 양면이 모두 신원 게이트를 통과한다:

- **발행자**: 도장/GIWA ID 검증 → `TokenFactory.issueAndList` (온체인, 배포 완료)
- **참여자**: 업비트 아이디 로그인(KYC) → 신규 상장 자산의 초기 거래 참여 자격

구현 계획: 참여 자격도 `IdentityRegistry` 어테스테이션을 재사용한다(발행자와
같은 원장, identityRef로 구분). 초기 참여 창은 DEX 상장 **앞단**의 별도
컨트랙트로 두어 "DEX 계층은 표준 V2 유지" 결정을 지킨다. 데모 단계에서는
터미널 로그인 동선에 업비트 아이디 옵션(준비 중)으로 표시하고, 실연동은
업비트 OAuth 제휴가 전제라 두나무 협의 사항으로 명시한다.

카피 금지선: "에어드랍"·"배분"·"상장 기대" 표현은 쓰지 않는다 (경품·사행성 및
상장 기대 마케팅 리스크 - §7 규제 포지션과 동일 축). 유저 방향 표현은 "검증
참여자에게 초기 거래 창이 열립니다"까지다.

## 3. 컨트랙트 아키텍처

```
                      ┌─────────────────────┐
   운영자(심사) ─attest─▶│  IdentityRegistry    │  신원 검증 원장
                      │  (IIdentityVerifier) │  · v1: 운영자 어테스테이션
                      └──────────┬──────────┘  · 도장/GIWA ID 어댑터로 교체 가능
                                 │ isVerified / identityRefOf
                      ┌──────────▼──────────┐
   발행자 ─issueAndList─▶│    TokenFactory      │  발행 게이트 (런치패드 코어)
   (검증된 신원만)       │                      │  · NaruToken 배포 + 공급 분배
                      └───┬─────────────┬───┘  · 발행 시점 identityRef 스냅샷
                          │ new         │ createPair + mint
                 ┌────────▼───┐   ┌─────▼────────────────────┐
                 │ NaruToken  │   │  Naruswap V2 (DEX 계층)   │
                 │ 고정 공급   │   │  Factory / Pair / Router  │
                 │ 특권 없음   │   │  V2 캐노니컬 시맨틱 유지     │
                 └────────────┘   └──────────────────────────┘
```

계층별 책임 분리가 핵심 결정이다:

- **DEX 계층은 퍼미션리스 V2 그대로.** 게이트를 DEX에 넣지 않는다. 표준 시맨틱을
  유지해야 기존 V2 툴링·인덱서가 그대로 붙고, 검증 정책이 바뀌어도 유동성 계층은 불변.
- **게이트는 TokenFactory 한 곳.** "검증 자산"의 정의 = 이 게이트를 거친 토큰.
  터미널 보드는 TokenFactory 레지스트리에 있는 토큰만 보여준다 - 검증 없는 토큰은
  DEX에 풀을 만들 수는 있어도 나루 터미널에 노출되지 않는다.
- **신원은 인터페이스 뒤에.** `IIdentityVerifier` 두 함수(isVerified/identityRefOf)만
  의존하므로 도장/GIWA ID 연동 시 TokenFactory 재배포 없이 어댑터만 교체한다.

## 4. 컨트랙트 상세

### IdentityRegistry (v1: 운영자 어테스테이션)

- `attest(subject, identityRef)` / `revoke(subject)` - onlyOwner(운영자)
- `identityRef`: 도장 어테스테이션 해시·GIWA ID namehash 등 검증 근거의 지문.
  **개인정보 원문은 온체인에 올리지 않는다.**
- revoke 정책: 회수하면 신규 발행은 막히지만, 기존 발행 토큰의 "발행 시점 검증됨"
  스냅샷(TokenFactory)은 불변 사실로 남는다. 인덱서는 두 상태(발행 시점/현재)를
  구분해 배지에 반영할 수 있다.

### TokenFactory (발행 게이트)

`issueAndList(name, symbol, totalSupply, liquidityTokens, metadataURI) payable`

1. `identity.isVerified(msg.sender)` 게이트
2. `NaruToken` 배포 (전량을 게이트가 수령)
3. 레지스트리 기록 + `TokenIssued` 이벤트 (identityRef 스냅샷 포함)
4. 선택적 상장: WETH 페어 생성 → 토큰·WETH 직접 예치 → `mint(발행자)` → `TokenListed`
   - 신규 페어라 슬리피지 개념이 없어 라우터 없이 페어와 직접 상호작용 (approve 동선 제거)
   - LP 토큰은 발행자 소유. **v1은 LP 락을 강제하지 않는다** - 검증된 신원이 책임
     주체라는 전제. 락 모듈은 로드맵 (§10)
5. 잔여 공급량은 발행자에게

파라미터 불변식: `liquidityTokens ≤ totalSupply`, `(liquidityTokens > 0) == (msg.value > 0)`.

### NaruToken

고정 공급 ERC-20. **mint/burn/owner/수수료 스위치/블랙리스트 표면 자체가 없다.**
발행자가 보유자 토큰에 손댈 수단을 제거하는 것이 신원 검증과 짝을 이루는 신뢰 모델이다.
프로비넌스(발행자·게이트 주소)는 immutable로 토큰에도 남겨 익스플로러에서 바로 보인다.

### Naruswap V2 (Factory / Pair / Router)

Uniswap V2 포크, Solidity 0.8.30 재작성. 캐노니컬 대비 의도적 차이와 이유:

| 변경 | 이유 |
|---|---|
| 플래시스왑 콜백 제거 | v1 범위 밖. 콜백 리엔트런시 표면 제거로 심사 시점 공격면 축소 |
| 프로토콜 수수료(feeTo/kLast) 제거 | 0.3% 전량 LP 귀속. 수수료 정책은 메인넷 단계 결정 |
| 라우터가 init code hash 대신 `getPair` 조회 | V2 포크 단골 사고(해시 불일치)를 구조적으로 제거 |
| 라우터 축소 (permit/FoT/ExactOut 계열 제외) | 나루 발행 토큰은 전부 표준 ERC-20 - 불필요 |

**바꾸지 않은 것**: 이벤트 시그니처(topic0), 준비금 uint112 배치, K 불변식과 수수료 수학,
MINIMUM_LIQUIDITY 잠금, TWAP 누적기. 가격 정의 `reserve1/reserve0`(CLAUDE.md 지표 정의)가
그대로 성립한다.

## 6. 보안 모델

- **러그 벡터의 구조적 제거**: NaruToken 특권 없음 · 커브/풀 파라미터 조작 표면 없음 ·
  게이트의 관리자 권한은 어테스테이션(attest/revoke)과 소유권 이전뿐
- **K 불변식**: 퍼즈 테스트(256런)로 "수수료가 있는 한 어떤 스왑도 K를 줄일 수 없다" 검증
  - LP 지급불능 방지의 핵심
- **리엔트런시**: 페어 `lock` 모디파이어(V2 동일) + 콜백 표면 제거. 라우터는 상태 없음
- **알려진 트레이드오프 (문서화하고 수용)**:
  - 운영자 어테스테이션은 중앙화 신뢰점 - v1의 의도된 설계이며 도장/GIWA ID로 대체 예정
  - LP 락 없음 - 검증된 신원의 책임으로 두되, 락 모듈을 로드맵에 명시
  - 시퀀서 단일 운영(두나무)은 체인 레벨 전제
- 배포/봇 지갑 분리, 키 커밋 금지는 CLAUDE.md 보안 규칙을 따른다

## 7. 규제 포지션 - 비증권 자산 전용

**나루는 증권성 없는 일반 가상자산만 상장한다. 증권형 토큰(STO)은 명시적으로
스코프 밖이다.** 2026-01-15 전자증권법·자본시장법 개정안 통과로 토큰증권은
전자증권법 발행 인프라와 증권사(투자매매·중개업자) 유통으로만 다루도록 제도가
확정됐다 - 즉 증권성 있는 토큰은 DEX 런치패드가 다룰 수 없음이 법으로 명확해졌고,
이는 나루의 경계선을 오히려 선명하게 만든다.

방어선은 세 겹이다.

1. **심사 단계(오프체인)**: 신청 → 검증 → 상장 흐름의 심사 체크리스트에 증권성
   판단을 포함한다. 수익 배분·이자·원금보장·바이백 약속이 있는 자산은 반려한다.
   퍼미션리스 런치패드에는 이 방어선 자체가 존재하지 않는다 - 검증 발행 구조의
   규제 측면 이점이다.
2. **코드 레벨**: `NaruToken`에는 배당·이자·수익분배 메커니즘이 없다. 고정 공급
   순수 전송 토큰이라 컨트랙트 차원에서 증권을 구성할 수단이 없다.

   - 증권성 판단 트리거가 되는 마케팅 표현을 원천 차단한다.

디지털자산기본법은 입법 전이다(2026-07 기준, 정무위 논의 중단 상태). 현 단계

변화가 재설계를 요구하지 않는다.
